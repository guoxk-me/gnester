## 结论 / Decision

**gnester 不设单一统一默认 transport，而是按交互语义分为两条 seam。** 当前 greeting/health 是必须返回结果的同步 request-reply seam，选择 `Transport.NATS`；未来需要 durable delivery 的 command/event 是另一条尚未实现的 seam，优先评估 `Transport.RMQ`，不将当前 Core NATS 当成统一业务总线。

**gnester has no single universal default transport; it separates two seams by interaction semantics.** The current greeting/health path is a synchronous request-reply seam that must return a result and therefore uses `Transport.NATS`. A future durable command/event path is a separate, not-yet-implemented seam for which `Transport.RMQ` should be evaluated first. The current Core NATS path is not a universal business bus.

### 当前 NATS seam 的持久性边界 / Durability boundary of the current NATS seam

当前 `Transport.NATS` 使用 Nest 页面所展示的 subject/Pub-Sub/queue-group 模型。**项目约束/推论：Core NATS 不为这条 seam 提供 durable storage 或 handler-level acknowledgement。** 这个结论是 gnester 对 Nest 官方 adapter 能力面的保守解读：页面只展示对 active subscribers 的 event delivery、queue group 分流和连接/关闭选项，没有 persistent stream、replay、offset 或 handler ack 配置。因此，当前 NATS seam 必须被视为 **non-durable**：可以用于 greeting/health 的在线 request-reply 和轻量 replica 分流，不能承载“稍后必须重放或确认处理”的 command/event。[NATS event-based](https://docs.nestjs.com/microservices/nats#event-based) [NATS queue groups](https://docs.nestjs.com/microservices/nats#queue-groups) [NATS options](https://docs.nestjs.com/microservices/nats#options)

The current `Transport.NATS` path uses the subject/Pub-Sub/queue-group model shown by Nest. **Project constraint/inference: Core NATS provides neither durable storage nor handler-level acknowledgements for this seam.** This is gnester's conservative interpretation of the official Nest adapter surface: the page shows event delivery to active subscribers, queue-group distribution, and connection/shutdown options, but no persistent-stream, replay, offset, or handler-ack configuration. The current NATS seam must therefore be treated as **non-durable**: it is suitable for online greeting/health request-reply and lightweight replica distribution, but not commands/events that must later be replayed or acknowledged as processed. [NATS event-based](https://docs.nestjs.com/microservices/nats#event-based) [NATS queue groups](https://docs.nestjs.com/microservices/nats#queue-groups) [NATS options](https://docs.nestjs.com/microservices/nats#options)

其他 transport 仍然按真实用例选择：gRPC 用于跨语言强 schema 的同步 RPC；Kafka 用于业务明确要求持久事件流、consumer group 和 offset 控制的场景；Redis Pub/Sub 不承载必须处理的业务消息。[gRPC overview](https://docs.nestjs.com/microservices/grpc#overview) [Kafka event-based messaging](https://docs.nestjs.com/microservices/kafka#event-based) [Kafka commit offsets](https://docs.nestjs.com/microservices/kafka#commit-offsets) [Redis semantics](https://docs.nestjs.com/microservices/redis#redis)

Other transports remain use-case driven: gRPC for strongly schematized cross-language synchronous RPC; Kafka when the business explicitly needs durable event streams, consumer groups, and offset control; and never Redis Pub/Sub for business messages that must be handled. [gRPC overview](https://docs.nestjs.com/microservices/grpc#overview) [Kafka event-based messaging](https://docs.nestjs.com/microservices/kafka#event-based) [Kafka commit offsets](https://docs.nestjs.com/microservices/kafka#commit-offsets) [Redis semantics](https://docs.nestjs.com/microservices/redis#redis)

## Nest 的统一编程模型 / Nest's canonical programming model

Nest 将微服务定义为使用非 HTTP transport layer 的应用。大多数依赖注入、decorator、exception filter、pipe、guard 和 interceptor 概念仍然适用；transport 通过同一套 request-response 与 event API 暴露，但具体投递语义仍由 transport 决定。[Overview](https://docs.nestjs.com/microservices/basics#overview)

Nest defines a microservice as an application using a transport layer other than HTTP. Dependency injection, decorators, exception filters, pipes, guards, and interceptors generally still apply. Transports expose a canonical request-response/event API, but their concrete delivery semantics remain transport-specific. [Overview](https://docs.nestjs.com/microservices/basics#overview)

### Request-response

- Server 端使用 `@MessagePattern()`，且该 decorator 只在 controller 中生效；放在 provider 中会被 Nest runtime 忽略。handler 可以同步返回、返回 `Promise`，也可以返回多次发值后完成的 `Observable`。[Request-response handlers](https://docs.nestjs.com/microservices/basics#request-response) [Asynchronous responses](https://docs.nestjs.com/microservices/basics#asynchronous-responses)
- Client 端 `ClientProxy.send(pattern, payload)` 返回 cold `Observable`，订阅后才实际发送。Nest 通常为 request 和 response 维护两个逻辑通道，因此不需要响应的流量不应滥用该模式。[Sending messages](https://docs.nestjs.com/microservices/basics#sending-messages) [Request-response channels](https://docs.nestjs.com/microservices/basics#request-response)

- On the server, `@MessagePattern()` is effective only in controllers; Nest ignores it in providers. A handler may return synchronously, return a `Promise`, or return an `Observable` that emits multiple responses before completion. [Request-response handlers](https://docs.nestjs.com/microservices/basics#request-response) [Asynchronous responses](https://docs.nestjs.com/microservices/basics#asynchronous-responses)
- On the client, `ClientProxy.send(pattern, payload)` returns a cold `Observable`; no message is sent until it is subscribed. Nest commonly maintains two logical request and response channels, so traffic that does not require a response should not pay this cost. [Sending messages](https://docs.nestjs.com/microservices/basics#sending-messages) [Request-response channels](https://docs.nestjs.com/microservices/basics#request-response)

### Event-based

- Server 端使用 `@EventPattern()`；同一进程内可为同一 pattern 注册多个 handler，Nest 会并行触发它们。[Event-based handlers](https://docs.nestjs.com/microservices/basics#event-based)
- Client 端 `ClientProxy.emit(pattern, payload)` 返回 hot `Observable`，即使调用方不显式订阅，proxy 也会立即尝试投递。这里的“立即尝试”不是持久化或成功处理保证，后者必须由具体 transport 页面证明。[Publishing events](https://docs.nestjs.com/microservices/basics#publishing-events)

- The server uses `@EventPattern()`. Multiple handlers may be registered for one pattern within an application, and Nest invokes them in parallel. [Event-based handlers](https://docs.nestjs.com/microservices/basics#event-based)
- `ClientProxy.emit(pattern, payload)` returns a hot `Observable`; the proxy immediately attempts delivery even without an explicit subscription. “Attempts delivery” is not a durability or successful-processing guarantee; only the selected transport can supply such semantics. [Publishing events](https://docs.nestjs.com/microservices/basics#publishing-events)

### Client lifecycle

- `ClientsModule.register()` / `registerAsync()` 是首选的可注入 client 建立方式；官方明确不推荐 `@Client()`，因为它更难测试，也更难共享实例。[Client producer class](https://docs.nestjs.com/microservices/basics#client-producer-class)
- `ClientProxy` 默认 lazy-connect，在第一次调用前建立并复用连接。若 broker 是服务启动的硬依赖，应在 `OnApplicationBootstrap` 中显式 `await client.connect()`，使连接失败阻止启动。[Client connection lifecycle](https://docs.nestjs.com/microservices/basics#client-producer-class)
- 调用方必须为 `send()` 管理超时；官方示例使用 RxJS `timeout()`。client/server 可订阅 transport-specific `status` stream、内部事件，并在高级场景通过 `unwrap()` 访问底层 driver。[Handling timeouts](https://docs.nestjs.com/microservices/basics#handling-timeouts) [Instance status](https://docs.nestjs.com/microservices/basics#instance-status-updates) [Underlying driver](https://docs.nestjs.com/microservices/basics#underlying-driver-access)

- `ClientsModule.register()` / `registerAsync()` is the preferred injectable-client mechanism. Nest explicitly discourages `@Client()` because it is harder to test and share. [Client producer class](https://docs.nestjs.com/microservices/basics#client-producer-class)
- `ClientProxy` connects lazily before the first call and reuses the connection. When the broker is a hard startup dependency, call and await `client.connect()` from `OnApplicationBootstrap` so connection failure blocks startup. [Client connection lifecycle](https://docs.nestjs.com/microservices/basics#client-producer-class)
- Callers must apply their own `send()` timeout; the official example uses RxJS `timeout()`. Clients and servers expose transport-specific status streams, internal events, and advanced driver access through `unwrap()`. [Handling timeouts](https://docs.nestjs.com/microservices/basics#handling-timeouts) [Instance status](https://docs.nestjs.com/microservices/basics#instance-status-updates) [Underlying driver](https://docs.nestjs.com/microservices/basics#underlying-driver-access)

### Hybrid application caveat

Hybrid app 的 microservice listener 默认**不会**继承主 HTTP app 的 global pipes、interceptors、guards 和 filters；只有 `connectMicroservice(..., { inheritAppConfig: true })` 才继承。[Sharing configuration](https://docs.nestjs.com/faq/hybrid-application#sharing-configuration)

A hybrid microservice listener does **not** inherit global pipes, interceptors, guards, or filters from the main HTTP application by default. Inheritance requires `connectMicroservice(..., { inheritAppConfig: true })`. [Sharing configuration](https://docs.nestjs.com/faq/hybrid-application#sharing-configuration)

gnester 当前目标是独立可部署服务，因此默认应继续使用每个服务自己的 `NestFactory.createMicroservice()` composition root，而不是依靠 hybrid inheritance。若某一进程确实同时监听 HTTP 与 broker，再显式启用并测试 `inheritAppConfig`。[Standalone microservice bootstrap](https://docs.nestjs.com/microservices/basics#getting-started) [Hybrid application](https://docs.nestjs.com/faq/hybrid-application#hybrid-application)

gnester targets independently deployable services, so each service should retain its own `NestFactory.createMicroservice()` composition root rather than rely on hybrid inheritance. If one process intentionally serves both HTTP and a broker listener, enable and test `inheritAppConfig` explicitly. [Standalone microservice bootstrap](https://docs.nestjs.com/microservices/basics#getting-started) [Hybrid application](https://docs.nestjs.com/faq/hybrid-application#hybrid-application)

## 当前 NATS seam 约束 / Current NATS seam constraints

以下约束只适用于当前 greeting/health 同步 request-reply walking skeleton，不会把 Core NATS 提升为 durable event bus。

The following constraints apply only to the current synchronous greeting/health request-reply walking skeleton. They do not promote Core NATS into a durable event bus.

1. **只使用 `send()` / `@MessagePattern()` 表达这两个需要响应的操作。** 当前不用 `emit()` / `@EventPattern()` 虚构尚未存在的 durable event 需求。Nest 区分 request-response 和 event API，NATS request-response 使用唯一 reply subject。[Request-response](https://docs.nestjs.com/microservices/basics#request-response) [NATS request-response](https://docs.nestjs.com/microservices/nats#request-response)
   **Use `send()` / `@MessagePattern()` only for these two response-bearing operations.** Do not use `emit()` / `@EventPattern()` today to invent a durable-event requirement that does not exist. Nest distinguishes request-response from event APIs, and NATS request-response uses a unique reply subject. [Request-response](https://docs.nestjs.com/microservices/basics#request-response) [NATS request-response](https://docs.nestjs.com/microservices/nats#request-response)
2. **同一服务的 replicas 配置同一稳定 `queue` 名。** NATS queue group 使每条消息仅由组内一个随机 subscriber 处理，用于这条 seam 的轻量水平分流。[NATS queue groups](https://docs.nestjs.com/microservices/nats#queue-groups)
   **Give replicas of one service the same stable `queue` name.** A NATS queue group has each message handled by one random subscriber in the group, providing lightweight horizontal distribution for this seam. [NATS queue groups](https://docs.nestjs.com/microservices/nats#queue-groups)
3. **每个 `send()` 都有调用方控制的 deadline。** Timeout 是调用方通过 RxJS operator 添加的，不是 `ClientProxy.send()` 的隐含保证。[Handling timeouts](https://docs.nestjs.com/microservices/basics#handling-timeouts)
   **Give every `send()` a caller-owned deadline.** Timeout behavior is added by the caller with an RxJS operator; it is not an implicit `ClientProxy.send()` guarantee. [Handling timeouts](https://docs.nestjs.com/microservices/basics#handling-timeouts)
4. **显式启用 `gracefulShutdown` 并设置有界 `gracePeriod`。** Nest 文档说明该选项会先 unsubscribe，再等待 grace period 后关闭；默认不启用。[NATS options](https://docs.nestjs.com/microservices/nats#options)
   **Enable `gracefulShutdown` explicitly with a bounded `gracePeriod`.** Nest documents that this option unsubscribes first and closes after the grace period; it is disabled by default. [NATS options](https://docs.nestjs.com/microservices/nats#options)
5. **将非持久边界写入 contract 和运维验收。** 项目约束/推论：queue group 只是分流；当前 Core NATS seam 没有 durable storage、replay、offset 或 handler ack，所以 broker/service 不可用时，调用方必须从 timeout/error 得到可预期失败，不得宣称请求会稍后重放。[NATS queue groups](https://docs.nestjs.com/microservices/nats#queue-groups) [NATS options](https://docs.nestjs.com/microservices/nats#options)
   **Put the non-durable boundary in the contract and operational acceptance criteria.** Project constraint/inference: a queue group only distributes work. The current Core NATS seam has no durable storage, replay, offsets, or handler ack, so callers must receive a predictable timeout/error when the broker or service is unavailable; the request must not be described as replayable later. [NATS queue groups](https://docs.nestjs.com/microservices/nats#queue-groups) [NATS options](https://docs.nestjs.com/microservices/nats#options)

## 未来 durable delivery 的 RMQ 评估约束 / RMQ evaluation constraints for future durable delivery

以下是未来引入 durable command/event seam 时的验收候选，不是当前 NATS seam 的配置。其中标注“推论”的内容不是 Nest 对 exactly-once 的承诺。

The following are acceptance candidates for a future durable command/event seam, not configuration for the current NATS seam. Items marked “inference” are not Nest promises of exactly-once processing.

1. **可靠业务 consumer 评估 `noAck: false`。** Handler 成功完成业务工作后才通过 `RmqContext.getChannelRef().ack(originalMessage)` 确认；consumer 在 ack 前失联时 RabbitMQ 会重新入队。[Message acknowledgement](https://docs.nestjs.com/microservices/rabbitmq#message-acknowledgement)
   **Evaluate `noAck: false` for reliable business consumers.** Acknowledge through `RmqContext` only after the handler finishes its business work; loss of the consumer before ack causes requeueing. [Message acknowledgement](https://docs.nestjs.com/microservices/rabbitmq#message-acknowledgement)
2. **显式压测并配置 `prefetchCount`。** 它是 Nest 暴露的 consumer flow-control 参数；数值应按 handler 并发、处理时长和下游容量确定。[RabbitMQ options](https://docs.nestjs.com/microservices/rabbitmq#options)
   **Load-test and configure `prefetchCount` explicitly.** Nest exposes it as consumer flow control; determine the value from handler concurrency, processing duration, and downstream capacity. [RabbitMQ options](https://docs.nestjs.com/microservices/rabbitmq#options)
3. **跨 broker restart 的消息同时验证 durable queue 与 `persistent: true`。** 官方把消息持久性限定为 queue 本身也能跨 restart 存活的情况。[RabbitMQ options](https://docs.nestjs.com/microservices/rabbitmq#options)
   **For messages that cross broker restarts, verify both a durable queue and `persistent: true`.** Nest conditions message persistence on the queue also surviving restarts. [RabbitMQ options](https://docs.nestjs.com/microservices/rabbitmq#options)
4. **推论：consumer 必须容忍重复投递。** 未 ack 时重新入队留下“副作用已产生但 ack 未到达”的失败窗口，因此 handler 需要业务幂等策略；Nest 没有承诺 exactly-once。[Message acknowledgement](https://docs.nestjs.com/microservices/rabbitmq#message-acknowledgement)
   **Inference: consumers must tolerate redelivery.** Requeueing without an ack leaves a failure window where a side effect may precede the ack, so handlers need business idempotency; Nest makes no exactly-once promise. [Message acknowledgement](https://docs.nestjs.com/microservices/rabbitmq#message-acknowledgement)
5. **验证 connection `status` 和 `error` 事件观测。** RMQ client/server 暴露 `connected`/`disconnected` status stream 和内部 error events；它们如何影响 readiness 是 gnester 的运维决策。[RMQ status](https://docs.nestjs.com/microservices/rabbitmq#instance-status-updates) [RMQ events](https://docs.nestjs.com/microservices/rabbitmq#listening-to-rabbitmq-events)
   **Verify observability of connection status and error events.** RMQ clients and servers expose connected/disconnected status streams and internal error events; how they affect readiness is a gnester operational decision. [RMQ status](https://docs.nestjs.com/microservices/rabbitmq#instance-status-updates) [RMQ events](https://docs.nestjs.com/microservices/rabbitmq#listening-to-rabbitmq-events)

## 不应从统一 API 推导的保证 / Guarantees not implied by the uniform API

- `emit()` 是 hot Observable 只表示 proxy 会立即尝试投递，不等于 broker 持久化、consumer 已处理或 exactly-once。[Publishing events](https://docs.nestjs.com/microservices/basics#publishing-events)
- `send()` 的 response 能证明 request-response 流程产生了响应，但不能替代 durable queue、manual ack 或业务幂等。[Request-response](https://docs.nestjs.com/microservices/basics#request-response) [RabbitMQ acknowledgement](https://docs.nestjs.com/microservices/rabbitmq#message-acknowledgement)
- Redis 的 `ClientProxy` 外形与 RMQ 相似，但 Redis transport 明确可能在无 subscriber 时丢失消息。[Redis](https://docs.nestjs.com/microservices/redis#redis)
- **项目约束/推论：**NATS queue group 只在 active replicas 间分流在线消息；它不为当前 Core NATS seam 提供消息持久化或 application-level handler ack，不能被当作 durable queue。该结论是对 Nest 页面已文档化能力面的保守边界。[NATS event-based](https://docs.nestjs.com/microservices/nats#event-based) [NATS queue groups](https://docs.nestjs.com/microservices/nats#queue-groups) [NATS options](https://docs.nestjs.com/microservices/nats#options)
- RMQ 的 `persistent` 是有条件的；只有 queue 同样跨 restart 存活时才满足官方描述的持久条件。[RabbitMQ options](https://docs.nestjs.com/microservices/rabbitmq#options)
- Kafka request-response 不是普通 RPC 的零成本替代：它需要 reply topic subscription、足够的 reply partitions，并会经历 consumer-group rebalance。[Kafka message pattern](https://docs.nestjs.com/microservices/kafka#message-pattern) [Response subscription](https://docs.nestjs.com/microservices/kafka#message-response-subscription)

- A hot `emit()` Observable means only that the proxy immediately attempts delivery; it does not mean broker persistence, successful consumer processing, or exactly-once behavior. [Publishing events](https://docs.nestjs.com/microservices/basics#publishing-events)
- A `send()` response demonstrates a completed request-response exchange, but it does not replace durable queues, manual acknowledgements, or business idempotency. [Request-response](https://docs.nestjs.com/microservices/basics#request-response) [RabbitMQ acknowledgement](https://docs.nestjs.com/microservices/rabbitmq#message-acknowledgement)
- Redis presents a familiar `ClientProxy` shape, yet its transporter explicitly loses messages when no subscriber is present. [Redis](https://docs.nestjs.com/microservices/redis#redis)
- **Project constraint/inference:** a NATS queue group only distributes online messages among active replicas. It supplies neither message persistence nor application-level handler acknowledgements for the current Core NATS seam and is not a durable queue. This is a conservative boundary drawn from the capabilities documented on the Nest page. [NATS event-based](https://docs.nestjs.com/microservices/nats#event-based) [NATS queue groups](https://docs.nestjs.com/microservices/nats#queue-groups) [NATS options](https://docs.nestjs.com/microservices/nats#options)
- RMQ `persistent` is conditional: the queue must also survive restarts for the documented persistence condition to hold. [RabbitMQ options](https://docs.nestjs.com/microservices/rabbitmq#options)
- Kafka request-response is not a zero-cost RPC substitute: it needs reply-topic subscriptions, enough reply partitions, and participation in consumer-group rebalances. [Kafka message pattern](https://docs.nestjs.com/microservices/kafka#message-pattern) [Response subscription](https://docs.nestjs.com/microservices/kafka#message-response-subscription)

3. 在任何 hybrid listener 上验证 `inheritAppConfig: true`；独立进程则分别注册同一套 pipe/guard/interceptor/filter provider。[Sharing configuration](https://docs.nestjs.com/faq/hybrid-application#sharing-configuration)

#### English

1. Make `@nestjs/microservices`, `nats`, and a reproducible NATS development environment the first infrastructure slice. Move the greeting/health walking skeleton to `Transport.NATS`, retain transport-independent contracts and caller-owned ports, and configure one stable queue group for replicas of the same service. [NATS installation](https://docs.nestjs.com/microservices/nats#installation) [NATS queue groups](https://docs.nestjs.com/microservices/nats#queue-groups)
2. Verify request-reply success, `RpcException`, caller timeout, no responder, two-replica distribution, disconnect/reconnect, and graceful shutdown. Results must match the non-durable contract and must not claim that requests published while offline can be replayed later. [Handling timeouts](https://docs.nestjs.com/microservices/basics#handling-timeouts) [NATS options](https://docs.nestjs.com/microservices/nats#options) [NATS status](https://docs.nestjs.com/microservices/nats#instance-status-updates)
3. Verify `inheritAppConfig: true` for every hybrid listener; independent processes should register the same pipe/guard/interceptor/filter providers independently. [Sharing configuration](https://docs.nestjs.com/faq/hybrid-application#sharing-configuration)

### 未来 durable seam / Future durable seam

#### 中文

1. 只有出现第一个真实 durable command/event 时，才先定义其 persistence、ack/requeue、ordering、replay 和幂等需求，然后优先评估 RMQ；不预先把当前 NATS seam 迁往 RMQ。
2. 若选择 RMQ，再增加 `amqplib`、`amqp-connection-manager` 和 RabbitMQ 开发环境，并验证 manual ack、handler failure 后 redelivery、`prefetchCount`、durable queue + persistent message，以及重复投递下的业务幂等。[RabbitMQ installation](https://docs.nestjs.com/microservices/rabbitmq#installation) [RabbitMQ options](https://docs.nestjs.com/microservices/rabbitmq#options) [RabbitMQ acknowledgement](https://docs.nestjs.com/microservices/rabbitmq#message-acknowledgement)
3. gRPC、Kafka、MQTT、Redis 或 custom transport 仍只在真实用例满足上面选择规则时引入；不为展示 Nest transport 数量而同时部署所有 broker。

#### English

1. Only when the first real durable command/event appears, define its persistence, ack/requeue, ordering, replay, and idempotency requirements, then evaluate RMQ first. Do not pre-emptively move the current NATS seam to RMQ.
2. If RMQ is selected, then add `amqplib`, `amqp-connection-manager`, and a RabbitMQ development environment and verify manual ack, redelivery after handler failure, `prefetchCount`, durable queues plus persistent messages, and business idempotency under duplicate delivery. [RabbitMQ installation](https://docs.nestjs.com/microservices/rabbitmq#installation) [RabbitMQ options](https://docs.nestjs.com/microservices/rabbitmq#options) [RabbitMQ acknowledgement](https://docs.nestjs.com/microservices/rabbitmq#message-acknowledgement)
3. Introduce gRPC, Kafka, MQTT, Redis, or a custom transport only when a real use case satisfies the selection rules above; do not deploy every broker merely to demonstrate the transports Nest supports.

- **Assumed for the recommendation:** the current greeting/health seam is synchronous, exposes failure through a response or timeout, and needs lightweight distribution among live replicas through a queue group. Durability, acknowledgement, and replay requirements for each future command/event must be evaluated from its business semantics.
